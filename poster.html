05 - Design Choices
Key Technical Decisions
Inline Everything on Workers
Serialized functions lose require() context when transmitted over RPC. The entire Porter stemmer (70 lines) and 130-word stoplist are pasted directly into the mapper function body. Workers execute completely self-contained functions with zero imports - no require('natural'), no external dependencies.
Coordinator-Driven Storage
Workers only fetch pages and return content via RPC. The coordinator performs all distribution[gid].store.put() calls itself, because workers lack the group proxy initialization needed to write to the distributed store. This centralizes state management and avoids race conditions.
SHA-256 Prefix Deduplication
Instead of storing full URLs in the visited/queued sets (avg ~80 chars each), we store 16-character SHA-256 prefixes. Cuts memory usage by ~5x while keeping collision probability negligible at 100K scale. Enables crawling 100K+ pages without OOM.
Streaming MR Results
Index results are never accumulated in a coordinator-side array. Each MR chunk's output is streamed directly to the distributed store with read-merge-write for overlapping terms. Prevents the coordinator from holding the entire inverted index in memory at once.
20s Worker Batch Timeout
Each fetchBatch RPC call enforces a 20-second safety timeout. If any URL hangs (common with rate-limited hosts), the worker returns whatever pages it successfully fetched. Prevents indefinite coordinator hangs during crawling.
Crash-Resumable Crawl State
Every 500 pages, the crawler serializes visited hashes, frontier queue, and URL chunks to the distributed store. On restart with --resume, state is loaded and crawling resumes exactly where it left off. Essential for multi-hour AWS crawls.
Round-Robin Wave Dispatch
Each crawl wave dequeues 30 URLs and distributes them round-robin across workers (10 per worker with 3 nodes). No centralized task queue needed - simple modular arithmetic achieves even load distribution across all workers.
06 - Distributed Crawling
Wave-Based BFS
Coordinator manages a 200K-entry frontier queue. Each wave dispatches 30 URLs round-robin to 3 workers via crawl-fetch RPC. Workers fetch pages, extract text via html-to-text, parse outlinks via regex, and return results. Coordinator stores content and deduplicates outlinks.

Target: Project Gutenberg - 70K+ free eBooks in HTML format. Seeded from the catalog; follows book pages, author pages, and bookshelves. Rich literary text ideal for TF-IDF ranking.
Dedup: 16-char SHA-256 prefix of each URL stored in Set objects. URL-to-hash conversion at insert + lookup time.
Persistence: State checkpointed every 500 pages. URL list stored in fixed-size chunks for streaming recovery on crash.
07 - Query & Retrieval
TF-IDF + PageRank
score(url) = Σ tf(t,url) · log(1 + N/(1+df)) · (1 + max(0, log(PR·N))) Per-term TF-IDF with logarithmic PageRank boost factor
Pipeline: Tokenize → Porter stem → dedup terms → parallel postings fetch from distributed store → TF-IDF score all candidates → PageRank boost → rank top 20 results.
Snippets: For each result, fetch stored page content and select the sentence with the highest query-term overlap. Matching tokens wrapped in <mark> for visual highlighting.
Web UI: Minimal black-and-white design. Each result displays page title, URL, highlighted snippet, numeric relevance score, and per-term tag breakdown showing individual term contributions.
08 - Extra Credit 4 Features
Beyond the Requirements
1. Iterative PageRank
PR(p) = (1-d)/N + d · Σq∈B(p) PR(q)/L(q) d = 0.85 · 10 iterations · dangling mass redistributed uniformly
Builds the complete link graph from crawled pages - only intra-corpus links count. Loads pages in batches of 50 from the distributed crawl store to avoid memory spikes. Dangling nodes (pages with no outlinks) redistribute their accumulated rank equally to all N pages at each iteration. The final {url: rank} map is stored in the index store under __pagerank__. The query engine loads this map once at startup and applies a logarithmic boost: score *= 1 + max(0, log(PR*N)), causing well-linked catalog and index pages to naturally rise in ranking.
2. Spell Check / Query Suggestions
When a query term returns zero hits from the inverted index, the engine generates all 1-edit-distance variants: character insertions, deletions, replacements, and transpositions. Each variant is checked against the distributed index store (top 30 candidates). If any variant has a document frequency ≥ 2, it's surfaced as "Did you mean: X?" in the search UI. Effectively handles typos like "shekespeare" → "shakespeare" or "philosphy" → "philosophy".
3. Highlighted Snippets & Titles
For each ranked result, the query engine fetches the full stored page content from the crawl group store. It splits the text into sentences, scores each by the count of query-term matches, and selects the best one. Matching tokens are wrapped in <mark> tags for visual highlighting in the UI. Page titles (extracted from <title> tags during crawling) are stored as metadata and displayed as clickable headings, giving results a familiar search-engine feel.
4. Debug / Status Endpoint
GET /status returns a live JSON dashboard: server uptime (formatted), total queries served since boot, total indexed documents, number of active worker nodes, V8 heap memory usage (used vs total in MB), and Node.js runtime version. Invaluable for monitoring long-running AWS deployments, diagnosing memory pressure, and confirming cluster health without SSH-ing into each node.
